Lesson 6 · 20 min

Network and file sandbox

A rule and a hook read the command; the sandbox reads nothing: the operating system simply won't let the process write outside the folder or open the network. But a sandbox can also fail silently. In this lesson you prove, with four escape attempts, what holds on your machine, and you see two locks that did not hold on this one.

Start the lesson

In this lesson you will

  1. 1Files and network: the two borders of the sandbox
  2. 2prova-isolamento.sh: four probes, one verdict
  3. 3Two locks that did not hold here: systemd --user and Claude without socat
  4. 4What the sandbox does not cover: reading outside the folder

Goal: prove on your machine that the sandbox blocks writes outside the folder and network access, instead of trusting the flag.

codex-cli 0.163.0, systemd 255. systemd accepted the flags and ran without them; the journal logged "PrivateNetwork=yes is configured, but the kernel does not support or we lack privileges for network namespace, proceeding without".

On this Ubuntu, kernel.apparmor_restrict_unprivileged_userns=1 stops the user's systemd from creating the namespaces. Codex only works here because bubblewrap got its own AppArmor profile (10/01/2026). On another machine it may be the other way around: that's why the proof runs on yours.

03 · Codex, Claude Code, and what each one isolates

According to each one's docs, read on 10/19/2026.

1. Codex

codex exec -s read-only or -s workspace-write runs the model's commands in a sandbox (on Linux, bubblewrap with a seccomp filter, per the codex sandbox docs). The docs recommend workspace-write for unsupervised local work and reserve --yolo for a runner that is already isolated.

codex sandbox -P [profile] -- [command] runs a command of yours in the sandbox, with no model: that's what the rehearsal uses. The :read-only and :workspace profiles were observed on 0.163.0.

2. Claude Code

sandbox.enabled puts Bash commands inside a system-level boundary: limited writes, and network only through a proxy with a domain list. On Linux it depends on bubblewrap and socat.

The sandbox covers shell commands; the file tools, MCP, and hooks run outside it (per the docs). For those, the rules from lesson 4 apply.

3. Fail loudly

By default, if the Claude Code sandbox can't start, it runs the commands without a sandbox. With sandbox.failIfUnavailable: true, it refuses to start.

In the loop, turn on failIfUnavailable: a missing lock has to stop the loop, not let it run wide open.

Claude Code docs"By default, if the sandbox can't start because a dependency is missing or the platform is unsupported, Claude Code runs commands without sandboxing."

04 · Claude Code: sandbox with explicit failure

This machine is missing socat. With failIfUnavailable, Claude Code refuses to start before any call to the model (it doesn't use your subscription quota).

Terminal · ask for the sandbox and require that it exists
cd /tmp/ensaio-seg/iso
claude --settings '{"sandbox":{"enabled":true,"failIfUnavailable":true}}' -p "responda só: ok" --tools ""
echo "saída: $?"
Example from the repository
Error: sandbox required but unavailable: sandbox is enabled but dependencies are missing: socat not installed · install missing tools (e.g. apt install bubblewrap socat) or see https://code.claude.com/docs/en/sandboxing
  sandbox.failIfUnavailable is set — refusing to start without a working sandbox.

saída: 1

Claude Code 2.1.303. Without failIfUnavailable, per the docs, the same session would have run the commands without a sandbox.

Install bubblewrap and socat (the error itself suggests apt install bubblewrap socat) and run it again: the session starts and responds. Then ask Claude to run the prova-isolamento.sh probes, one at a time, and check for BLOQUEADO on escreve-fora and rede.
